zenbench workflow guide

Measurement assumptions, busy workstations and external A/B:
  zenbench guide --topic methodology

EDIT / EXPLORE
  cargo bench --bench kernels -- --help
  cargo bench --bench kernels -- --group=filter
Iterate is the default. Check correctness first; compare alternatives in one
interleaved group when practical. Treat local intervals as exploratory. Freeze
the candidate, inputs, margin and plan before a separate confirmation run.

CPU PLACEMENT / RAYON
  zenbench cpu-info
  zenbench exec --cpu-policy performance cargo -- bench --bench kernels -- --group=filter
Select detected CPU IDs explicitly for unequal cache classes; do not assume
which is faster. Use separate launches/results for P/E or cache classes.
Linux needs a matching hard cpuset (or a delegated systemd cpuset controller).
Windows uses an inherited Job boundary on supported topology. macOS class binding
and Windows ARM/multiple-group classification are unsupported. A thread hint or
taskset cannot constrain arbitrary pools that widen their masks. Register Rayon
work with bench(); do not wrap it in bench_parallel/bench_contended. Configure the
pool size yourself. Probes observe new workers; they do not certify hidden pools.
Unrestricted is an explicit exploratory opt-out, never a confirmation remedy.

BACKGROUND EXPLORATION
  zenbench run kernels --cargo-args="-- --group=filter"
  zenbench list
  zenbench results latest
Use status RUN_ID to track a run. For confirmation use direct cargo bench or a
retained executable: the background wrapper does not preserve decision exit codes.
Its --wait timeout does not bound the initial Cargo child wait.

CONFIRM AN EDIT / CI
After selecting a verified CPU boundary, on the control build:
  cargo bench --bench kernels -- --mode=confirm --workload-id=inputs-v1 --dry-run
  cargo bench --bench kernels -- --mode=confirm --workload-id=inputs-v1 --save-baseline=before
On the frozen candidate, using the same inputs, case inventory and settings:
  cargo bench --bench kernels -- --mode=confirm --workload-id=inputs-v1 --baseline=before
Add --update-on-pass only to deliberately promote a confirmed candidate.
Confirm defaults to five fresh processes with fixed rounds. Set --margin=PERCENT
and --confidence=FRACTION before measuring; do not tune them to get a pass.
Exit 0: all cases non-inferior; 1: confirmed regression; 2: invalid/inconclusive.
Iterate exit 0 only means execution succeeded. Initial baseline creation makes
no improvement claim. Historical controls are not randomized contemporaneous A/B.
If INVALID, fix the reported placement/inventory/storage/observation problem.
If INCONCLUSIVE, retain it; choose and report a new plan, not repeated favorable looks.

COMPARE SOURCE REVISIONS
  zenbench self-compare --bench kernels --ref HEAD~1 --cargo-args="-- --group=filter"
Builds the old ref and current working tree, including local edits. Runs baseline
then candidate, retains both packets, and reports their comparison. This is an
exploratory convenience; default results return comparison exit 2. It does not
randomize binary order or establish a validated A/B experiment.

KEEP TWO BUILDS
Keep immutable copies of the two zenbench benchmark executables and their runtime
assets outside Cargo's replaceable target directory. Run each directly with the
same working directory, input/configuration and verified CPU boundary. They accept
the same --mode/--group flags as cargo bench after --. Set ZENBENCH_RESULT_PATH to
a different fresh .json.gz path for each run, then:
  zenbench compare before.json.gz after.json.gz
This compares recorded results; it does not launch executables. There is no
dedicated two-binary runner or automatic source-to-binary build manifest today.
Record toolchain, target, features, flags, allocator, dependencies, input hashes,
Git commit and clean/dirty state at build time beside each executable. Saved
execution.binary_sha256 identifies the executable bytes. Saved git_hash is runtime
HEAD in the working directory, not the source used to build a retained executable.
Clean/dirty status, patches and source digests are not automatically captured.

EVIDENCE / MULTIPLE MACHINES
  cargo bench --bench kernels -- --mode=evidence --workload-id=inputs-v1 --scope=linux/performance/filter
Evidence runs one named matrix cell with Confirm's protocol. You own the matrix,
correctness controls, build provenance and artifact backup. Do not merge unlike
hardware/core classes into one baseline. This command does not schedule a fleet
or certify publication readiness. Warmup is not proof of maximum CPU frequency.

READ / KEEP SMALL GIT DIFFS
  zenbench read candidate.json.gz
  zenbench read candidate.json.gz --format json
  zenbench compare baseline.json.gz candidate.json.gz
  zenbench snapshot candidate.json.gz --output benchmarks/baseline.csv
  zenbench reanalyze candidate.json.gz --output analysis.json
Raw rounds/processes live in ignored .zenbench/data (ZENBENCH_DATA_DIR overrides).
Commit selected stable CSV summaries, not every run. Back up full gzip objects;
references alone are not portable. CSV is not comparison input. Read/decode/compare
commands are embedded in saved references/snapshots and gzip header guidance.
Reanalysis replays the frozen policy; it cannot promote exploratory data.

SIMD OPTIMIZATION
  zenbench guide --topic simd
Archmage/magetypes: runtime versus compile-time summoning, held-token comparisons,
correctness differentials, cargo asm, A/A controls and end-to-end confirmation.

PROFILE WHY
AllocProfiler is opt-in installation as the benchmark's global allocator; enabling
the feature alone does not install it. It updates thread-local counters and a
shared relaxed atomic activity flag on allocations. This adds work to allocation/deallocation/reallocation paths, included in timed samples.
No universal overhead figure is established. Keep instrumentation identical for
both arms; confirm native timing separately without it. Counts cover the measured
thread, not allocations on external Rayon workers, and are not peak-live memory.
Heaptrack and iai-callgrind are complementary external tools, not integrated
backends. Use separate profiling workloads/runs and retain their artifacts with
binary/input identity. Profiler-instrumented timing is not a native timing baseline.
